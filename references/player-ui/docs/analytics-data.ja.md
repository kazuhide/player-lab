# Analyticsデータからグラフを計算する

[English](analytics-data.md) · [日本語](analytics-data.ja.md) · [起動方法](../README.ja.md)

このグラフの「見られた区間」（`reach`）と「見返された区間」（`replay`）は、
再生範囲から計算するPlayer Lab独自の指標です。Analyticsの標準指標や
DashboardのEngagementをそのまま表示したものではありません。
通常のリファレンスは合成データの集計結果を読み込み、Analyticsへの問い合わせは行いません。
[非公開データ用のローカル画面](private-query-data.ja.md)では、外部ファイルの集約Query件数を読み込み、
区間を見た再生記録の割合を別の指標として表示できます。

| 取得方法 | 見られた区間 | 見返された区間 |
| --- | --- | --- |
| サンプル単位のExport | 現在の定義で計算できる | 繰り返した再生範囲から計算できる |
| QueryとImpression Details | 必要なサンプルが揃えば同じ計算を適用できる | パスの境界が分かれば同じ計算を適用できる |
| 集約Queryのみ | 区間を見た再生記録の割合を求める。現在とは異なる指標 | 件数や再生時間の合計だけでは判定できない |

## 値の意味

再生記録はAnalyticsのimpression、つまり1回の再生セッションに対応します。
異なる人の数ではありません。動画内の区間を`B`、集計対象となる再生記録の総数を`N`とします。
`N`には、区間`B`に到達しなかった記録も含めます。対象は本編の再生が観測された記録で、
広告や再生中ではない状態は視聴範囲に加えません。

記録ごとに、一続きの再生をパスとして扱います。戻るシークの後は別のパスです。
同じパス内で画質変更などにより分割・重複した範囲をまとめ、シークで飛ばした距離は含めません。
全パスを重ねて1回以上再生した範囲が「見られた区間」、
別のパスで2回以上再生した範囲が「見返された区間」です。
同じ記録で何度見返しても、その範囲の長さは1回分までとします。[集計コード](../src/engagement.ts)も参照してください。
動画内の長さを使うため、低速再生だけでは値は増えません。

```text
見られた割合 = 各記録で「1回以上再生した部分」の区間B内の長さの合計 ÷（Bの長さ × N）
見返された割合 = 各記録で「2回以上再生した部分」の区間B内の長さの合計 ÷（Bの長さ × N）
```

20秒から22秒までの2秒間を例にします。

| 記録 | 再生した範囲 | この区間で見た長さ | この区間で見返した長さ |
| --- | --- | --- | --- |
| A | 20–22秒を再生し、21秒へ戻って21–22秒を再生 | 2秒 | 1秒 |
| B | 20–21秒を再生 | 1秒 | 0秒 |
| C | 0–10秒のみ再生 | 0秒 | 0秒 |

`N = 3`なので、見られた割合は`3 ÷ (2 × 3) = 50%`、
見返された割合は`1 ÷ (2 × 3) ≈ 16.7%`です。
一方、この区間を少しでも見た記録の割合は`2 ÷ 3 ≈ 66.7%`になります。
記録Bは区間の半分だけを見ていますが、件数による計算では1件として数えるためです。
`support`はその区間の再生が観測された記録数で、この例では2件です。分母には全体の3件を使います。

カードの小グラフは同じ0–100%の目盛です。映像上では選んだ分布の最大値に合わせて高さを拡大します。
どちらも、場面が盛り上がった確率を示すものではありません。
視聴が観測され、見返しがない区間の`replay`は`0`です。観測のない区間は`null`を保ちます。
取得に失敗した場合も、実測のゼロに置き換えてはいけません。

## サンプル単位のExportを使う

1. 動画の識別子とバージョン、Analyticsライセンス、UTCの集計期間を決めます。
   両方の指標とすべての区間で同じ条件を使います。
2. `POST /v1/analytics/exports/`でExportを作成します。
   [リクエスト例](examples/export-task.json)はParquet形式と、作成済みのAnalytics出力先を使います。
   `FINISHED`になったことを確認し、出力ファイルをすべて取得します。
3. 実ファイルの列を下表のフィールドへ変換します。単位、状態の値、欠損、順序を確認してください。
4. 再生記録とシーケンス番号で重複を除き、パスを復元して上の式を適用します。
   同じ番号で値が異なる記録や、シークの記録がない逆方向の時刻変化は、再視聴と決めずに調べます。
5. 検証済みの集計値だけをCMSへ保存します。処理が完了した単位で一括公開し、
   個別の視聴履歴とアカウントAPIキーはサーバーに保持します。

ExportはCSVとParquetに対応し、結果は1時間ごとのファイルに分かれます。
例では`columns`を指定せず、順序や状態の列を取りこぼさないようにしています。
詳細は[公式のExportガイド](https://developer.bitmovin.com/playback/docs/exporting-your-data)を参照してください。

| 必要な情報 | デモで使うフィールド | 用途 |
| --- | --- | --- |
| 動画の識別子と長さ | `videoId`, `videoDuration` | 動画のバージョンと位置を一致させる |
| 再生記録と送信順 | `impressionId`, `sequenceNumber`, `time` | 記録ごとの復元と重複除去 |
| 動画内の再生位置 | `videotimeStart`, `videotimeEnd` | ミリ秒単位で各区間との重なりを求める |
| 再生時間と状態 | `played`, `state` | 停止・バッファリング・シークを除外し、シークの記録を保つ |
| 広告の区別 | `ad` | 本編以外の再生を除外する |

表は変換後のフィールド名です。CSVの列名がこの綴りになるとは限りません。
[Analyticsのフィールド仕様](https://developer.bitmovin.com/playback/docs/analytics-api-fields)と
[サンプルのモデル](https://bitmovin.github.io/bitmovin-api-sdk-php/classes/BitmovinApiSdk_Models_AnalyticsImpressionSample.html)を参照し、
実ファイルのスキーマに合わせて読み込み処理を用意します。
デモの`DemoExport`は合成データ専用の構造であり、Export APIの応答ではありません。

## Queryと再生記録の詳細を使う

Exportタスクを作成せずに取得する方法です。Queryで対象の再生記録を選び、
Impression Detailsからサンプルを取得します。集計はサーバー側で行います。

1. [ID列挙用のリクエスト](examples/query-impression-ids.json)を
   `POST /v1/analytics/queries/count`へ送ります。
   上と同じ対象条件を使い、`IMPRESSION_ID`でまとめてIDの昇順に並べます。
2. `limit: 200`と`offset`で続きのページを取得し、200行未満または空のページまで進めます。
   IDの重複を除いて保持してください。IDごとの集約値の合計では代用できません。
   行内の列位置は`columnLabels`で確認します。
3. 各IDの`POST /v1/analytics/impressions/{impression_id}`へ
   [ライセンスを指定する本文](examples/impression-details.json)を送ります。
   サンプルを変換し、順序、状態、動画内の位置が揃っていることを確認します。
4. 指定した集計期間にサンプルを揃え、Exportと同じパス・区間の集計を実行します。
   有効な本編再生が確認できた記録から`N`を数え直します。ID列挙は候補を選ぶ操作であり、
   元データの検証に代わるものではありません。
   分母となる再生記録の範囲と、取得が完全かどうかの判断も一致させます。

`limit`と`offset`は[Count API](https://developer.bitmovin.com/playback/reference/postanalyticsqueriescount)、
詳細取得のRESTエンドポイントは[Impression Details API](https://developer.bitmovin.com/playback/reference/showimpressiondetails)に記載されています。
すべてのAPI SDKに詳細取得のメソッドがあるとは限らないため、上記RESTエンドポイントを使います。

詳細の取得時には再生時間に加算しない停止・シーク・広告のサンプルも保持します。
先に`PLAYED > 0`だけへ絞ると、パスを区切るための記録を失うおそれがあります。
ID列挙時のフィルターは対象の再生記録を選ぶ条件であり、後から取得するサンプルを削る条件ではありません。

## 集約Queryだけを使う

見られた区間の軽量な代替として、`POST /v1/analytics/queries/count`の
`dimension: "IMPRESSION_ID"`を使えます。

- [全体の件数を求めるリクエスト](examples/query-population.json)は、
  `VIDEO_ID`、`PLAYED > 0`、`AD = 0`で動画全体の対象記録を数えます。
- [区間の件数を求めるリクエスト](examples/query-watched-overlap.json)は、
  同じ条件に`[20000, 22000)`ミリ秒との重なりを追加します。

```json
[
  { "name": "VIDEOTIME_START", "operator": "LT", "value": 22000 },
  { "name": "VIDEOTIME_END", "operator": "GT", "value": 20000 }
]
```

区間の件数を全体の件数で割ると、**その区間を少しでも見た再生記録の割合**になります。
区間内で見た長さによる現在の指標とは区別してください。
開始・終了位置が両方とも区間内にある、という条件では区間の境界をまたぐサンプルを落としてしまいます。
Queryの`interval: "MINUTE"`は収集時刻を分ける指定であり、動画内の区間幅ではありません。
[Queryのリクエストモデル](https://github.com/bitmovin/bitmovin-api-sdk-javascript/blob/f7a36bc3e7b399bed003fe9374a8f865d556cd07/src/models/AnalyticsQueryRequest.ts)も参照してください。

画質別に分けずに再生記録を数えます。画質変更をした記録が複数のグループに現れるため、
画質別の件数を足すと同じ記録を重複して数えることがあります。
`SUM(PLAYED)`は見返しも含む再生時間の合計であり、範囲の重複除去や記録ごとの上限を適用する計算ではありません。
公式の例でも[再生記録の件数と再生時間](https://developer.bitmovin.com/playback/docs/how-to-recreate-dashboard-queries-via-the-api-1)は分けて扱っています。

### Queryの件数から再視聴を求めない理由

重なるサンプルが複数あっても、同じパスが分割されただけかもしれません。
再視聴を判定するには、サンプル数や再生時間の合計、ある位置に到達した記録数だけでなく、
順序を保ったパスが必要です。

Queryで順序付きのサンプル相当データを取得する方法も調べました。
2026年11月16日の認証付きの確認では、`SEQUENCE_NUMBER`と`STATE`によるgroupByはAPIに拒否されました。
`SEQUENCE_NUMBER`のように公開された[属性の列挙型](https://github.com/bitmovin/bitmovin-api-sdk-javascript/blob/f7a36bc3e7b399bed003fe9374a8f865d556cd07/src/models/AnalyticsAttribute.ts)に名前があっても、
groupByに使えることを示すものではありません。この方法はExportや詳細取得の代わりには使えません。
`SEEKED`もシークにかかった時間であり、パスの識別子や元の状態の並びを置き換えるものではありません。

取得できない再視聴の値を`0`で埋めてはいけません。合成データの検証処理は観測済み区間の両指標と、
デモ用の指標バージョンを要求します。[非公開データ用のQuery画面](private-query-data.ja.md)は
別の検証処理と`watched-impression-incidence-v1`の形式を使い、再視聴は取得なしと明示します。

## バッチ処理とCMSへの保存

リクエストはバックエンドやバッチから`X-Api-Key`付きで送ります。
本文の`licenseKey`はAnalyticsライセンスであり、アカウントAPIキーとは別です。
JSONの例には仮の値が入っています。リポジトリ外へコピーして置き換えてください。

集計期間を固定し、並び順を揃え、同時に取得する件数へ上限を設けます。
再生記録を一つずつ処理してメモリ使用量を抑え、動画のバージョンと期間をキーに結果を再利用します。
動画の再生時にはCMSの集計結果を使うため、視聴のたびに詳細取得を行う必要はありません。
大量の履歴にはExport、小さく絞った対象や追加分の処理にはQueryと詳細取得の組み合わせが適しています。

イベント単位の詳細データは、契約により30日または90日保持されます。
セッションを1行へ圧縮した集計結果から複数のパスは復元できません。
集計期間を決める前に[データの保持期間](https://developer.bitmovin.com/playback/docs/data-aging-in-bitmovin-analytics)を確認してください。
ページの欠落、保持期間を過ぎたサンプル、途中で切れた記録を、完全な「再視聴なし」として公開してはいけません。

合成データ用の集計処理は実データを受け付けません。ガードを避けるために、実際のExportへ
`synthetic: true`を付けてはいけません。非公開データ用の画面が検証するのは集計済みのQuery件数だけです。
Exportの実ファイルやImpression Detailsの変換処理、本番のデータ配信は、利用するアプリに合わせて実装してください。
[事前集計とCMS連携](../README.ja.md#再生前にデータを準備する)も参照してください。
